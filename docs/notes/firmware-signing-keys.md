# Firmware Signing Keys — dev vs production, and the key ceremony

2026-09-06 · spaxel-5bf35319 · parent spaxel-8aa9703c (ADR-004 OTA security
hardening) · prerequisite spaxel-497aee78 (anti-rollback secure_version)

Companion records: [ADR-004 OTA security](adr-004-ota-security.md),
[anti-rollback secure version](anti-rollback-secure-version.md)

The production firmware signing key now has a sanctioned home in OpenBao.
This document is the key ceremony: how the key was generated, where it lives,
how a build consumes it without the key material crossing a terminal, a log
or a transcript, how rotation works, and what losing the key actually means.

## Where the production key lives

| | |
|---|---|
| Instance | `openbao-v2` (ardenone-cluster, authoritative since 2026-08-29) — `bao-as openbao-v2 …` |
| Path | `secret/ardenone-cluster/spaxel/firmware-signing/prod` |
| Current version | 1 (provisioned 2026-09-06) |
| Scheme | RSA-3072, Secure Boot V2 (the only RSA size the scheme supports) |
| CAS | mount-level `cas_required=true` — every write passes `-cas=<current_version>` |
| History | mount default `max_versions=20` — old versions are retained, never destroyed |
| Public key digest (SPKI DER, SHA-256) | `03c6cc1ed6b5d44a97139da0977b896562fda87bfedd15d2e8b944c6c4720692` |

Stored fields:

- `key_pem` — the RSA-3072 private key (PEM). **Never displayed anywhere.**
- `public_key_pem` — the public half, for signature verification without
  touching the private key.
- `public_key_spki_sha256` — identifier for the public half. This is *not*
  the eFuse `SECURE_BOOT_KEY_DIGEST*` value; IDF derives that from the key in
  its own way and the authoritative source is `espefuse.py summary` on a
  provisioned device.
- `scheme`, `esp_idf`, `purpose`, `generated_at`, `generated_by`,
  `ceremony_doc` — metadata that travels with the key.

Notes on the store itself: agents cannot delete anything on OpenBao
(2026-08-31), so the key cannot be lost to an errant `bao kv delete`; a
"rotation" is a new version at the same path; and the provisioning identity
used for the write (`coding-agent-provision`) is write-only — it cannot read
the value back, which is why every verification below is metadata-only.

## Dev key vs production key

| | Development | Production |
|---|---|---|
| Generated by | `generate-signing-key.sh` (default mode), self-serve | The key ceremony below, exactly once |
| Lives in | `firmware/keys/` (gitignored) | OpenBao, path above |
| Signs | bench-board images | fleet images |
| Loss impact | regenerate, reflash the bench board | every fielded node is stranded on its last signed image — see below |
| Who can read it | whoever has the file | `coding-agent` OpenBao policy on `openbao-v2` (and the operator) |

A dev key must never be promoted to the prod path and the prod key must never
be copied into `firmware/keys/`.

## Key ceremony

What generates the key, and why it happens on ex44: ideally key material is
generated inside the cluster under a workload identity, but `espsecure.py`
needs the pinned ESP-IDF 5.2 python environment, which lives on ex44. So the
key is generated *in place* on ex44 — in a RAM-backed working directory — and
delivered to OpenBao by file reference, never as an argument. This is the
"ex44 generates it under the provisioning identity" route from the workspace
secrets policy, and the plaintext never exists anywhere readable.

```bash
set -euo pipefail
SCRIPTS=/home/coding/spaxel/firmware/scripts
PATH_SECRET=secret/ardenone-cluster/spaxel/firmware-signing/prod

# RAM-backed working directory: the plaintext never touches a disk
TMPD="$(mktemp -d /dev/shm/spaxel-prodkey.XXXXXX)"
chmod 700 "$TMPD"
trap 'shred -u "${TMPD}"/* 2>/dev/null; rm -rf "${TMPD}"' EXIT

# 1. generate — private key on stdout, public half to --pubout, chatter on stderr
"$SCRIPTS/generate-signing-key.sh" --stdout --pubout "${TMPD}/pub.pem" \
    > "${TMPD}/key.pem" 2> "${TMPD}/gen.log"

# 2. property check (never a string match on the material)
openssl pkey -in "${TMPD}/key.pem" -noout -check

# 3. public identifier — public information, safe to record anywhere
DIGEST="$(openssl pkey -pubin -in "${TMPD}/pub.pem" -outform DER \
          | openssl dgst -sha256 | awk '{print $NF}')"

# 4. assemble the payload — jq reads the files; nothing is printed
jq -n --rawfile key "${TMPD}/key.pem" --rawfile pub "${TMPD}/pub.pem" \
      --arg digest "$DIGEST" --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
      '{purpose: "ESP32-S3 Secure Boot V2 production firmware signing key",
        scheme: "rsa3072", esp_idf: "5.2",
        key_pem: $key, public_key_pem: $pub,
        public_key_spki_sha256: $digest, generated_at: $now,
        generated_by: "firmware/scripts/generate-signing-key.sh --stdout --pubout",
        ceremony_doc: "docs/notes/firmware-signing-keys.md"}' \
   > "${TMPD}/payload.json"

# 5. write once, CAS-guarded, under the WRITE-ONLY identity
CAS="$(bao-as openbao-v2-provision bao kv metadata get -format=json "$PATH_SECRET" \
        | jq .data.current_version)"     # 0 when the path does not exist
bao-as openbao-v2-provision bao kv put -cas="$CAS" "$PATH_SECRET" @"${TMPD}/payload.json"

# 6. verify by METADATA ONLY — the provisioning identity cannot read values
bao-as openbao-v2-provision bao kv metadata get -format=json "$PATH_SECRET" \
  | jq .data.current_version             # must be CAS+1
```

Rules that make this a ceremony and not just a command:

- The value never appears in argv (`@file`, not a literal), in the transcript,
  in a log, or in a repo path. A bare `bao kv get` of the path dumps the key
  to the terminal and is forbidden; a bare `bao kv put key_pem=<pem>` puts it
  in `ps` and shell history and is likewise forbidden.
- Verification is by property and metadata: `openssl pkey -noout -check`
  before the write, `current_version` after it. Reading the key back and
  printing it "to check" is the one thing the whole design exists to prevent.
- The shred trap runs even on failure, so an aborted ceremony leaves nothing
  behind in `/dev/shm`.
- `deletion_time` must read `n/a` in the post-write metadata. A stamped
  `delete_version_after` on this mount would have expired the only version of
  a write-once path.

## How a build obtains the key

The key is fetched straight into the signer's stdin, so it exists only in
flight — never on disk, never in argv, never in a log:

```bash
bao-as openbao-v2 bao kv get -field=key_pem \
    secret/ardenone-cluster/spaxel/firmware-signing/prod \
  | ./scripts/sign-firmware.sh --key-fd 0 build/spaxel.bin build/spaxel-signed.bin
```

`sign-firmware.sh --key-fd N` hands `/dev/fd/N` to `espsecure.py sign_data`,
whose `--keyfile` opens a path — a pipe works. Verification of a signed image
uses only public material:

```bash
bao-as openbao-v2 bao kv get -field=public_key_pem \
    secret/ardenone-cluster/spaxel/firmware-signing/prod > /dev/shm/pub.pem
espsecure.py verify_signature --version 2 --keyfile /dev/shm/pub.pem signed.bin
```

This exact pipeline was exercised against the stored key on 2026-09-06: the
read signed a test image through `--key-fd 0`, and `verify_signature`
accepted it against the stored `public_key_pem`. The check was recorded by
result, not by value.

### CI gap — deliberately not solved here

`spaxel-build` on iad-ci has no OpenBao identity, so CI builds unsigned
images. Enabling production signing in CI needs a kubernetes-auth AppRole for
the build namespace plus a decision about serving the key into a shared CI
runner at all — a shared runner is a poor custodian of a key whose loss ends
OTA for the fleet. Until that decision is made, production-signed images are
produced manually via the pipeline above. Tracking that decision belongs to
the ADR-004 chain, not to this bead.

### Build-integration status

Signing infrastructure and key custody are in place; **secure boot
verification is not yet enabled in the build** (`CONFIG_SECURE_BOOT` is not
set in `firmware/sdkconfig.defaults`, so nothing checks signatures at boot
yet). Note that `CONFIG_SECURE_BOOT_V2` — the symbol referenced by some older
comments — never existed in ESP-IDF 5.x. Enabling it, and provisioning the
public key digest into the bootloader/eFuse on real hardware, is the
remaining ADR-004 work; this document covers key management only.

## Rotation policy

There is **no calendar rotation**. Each rotation is a physical event: a
transitional dual-signed release plus an irreversible eFuse burn on every
node (which needs hands on the hardware). Rotate only on key compromise,
suspected compromise, or a custody change.

Mechanics, in order:

1. **Write the new key** to the same OpenBao path as a new version
   (`-cas=<current+1>`), via the same ceremony. History is retained
   (`max_versions=20`), so the old key remains recoverable while the
   transitional release ships. Do not create a second path — "which key is
   current" must have one answer.
2. **Dual-sign the transitional release.** ESP32-S3 trusts up to three key
   digests, and `sign-firmware.sh --keyfile/--key-fd` is repeatable; espsecure
   writes one signature block per key in a single pass (no
   `--append_signatures` needed for a fresh image):
   `sign-firmware.sh --key-fd 0 --keyfile new_prod.pem in.bin out.bin`.
   Nodes running firmware that trusts the old digest accept this image, and
   its signature blocks teach the bootloader the new digest.
3. **Let the fleet converge**, then **burn the revocation eFuse per node**:
   `espefuse.py --port <port> burn_efuse SECURE_BOOT_KEY_REVOKE0` (block index
   of the retired key). Irreversible, physical access only, and only safe
   once every node runs the dual-signed release — burning a digest the
   bootloader still needs bricks the node.
4. **Ship new-key-only releases** afterwards.

The eFuse budget is the hard limit: three digests total, ever. Two full
rotations consume it.

## If the production key is lost

Losing the key — as opposed to an attacker stealing it — is **unrecoverable
for OTA**, and no amount of OpenBao discipline changes that:

- The trusted digests live in write-once eFuse. You cannot *add* a replacement
  digest without a signature chain rooted in a key you control, and you cannot
  produce one without the private key.
- Revocation does not help: `SECURE_BOOT_KEY_REVOKE*` retires a digest, it
  does not admit a new one. Burning it on a lost key just guarantees the
  fleet accepts nothing you can produce.
- Every fielded node runs its last validly-signed image forever. OTA is dead
  fleet-wide; recovery means physical re-flashing of every board, and under
  permanently-enabled secure boot even that requires a bootloader signed by a
  trusted key.

So the two mitigations address two different threats:

- **Exposure** is what OpenBao controls: versioned storage, CAS, a write-only
  provisioning identity, no agent-readable copies outside the read policy.
- **Loss** is what OpenBao cannot control — an instance-level failure that
  takes the path with it. That is why the operator should hold an **offline
  escrow copy** (cold storage, treated like a root CA). Making that copy is a
  human action outside the agent boundary: agents must never create private
  key copies in a repo, a scratch directory, or a transcript, and the escrow
  is exactly such a copy.

If the key is *compromised* (attacker has it) rather than lost: do not rely
on it, rotate per the section above, and burn the old digest's revocation
eFuse on every node. Between compromise and completed rotation, the attacker
and you can both sign images — which is why the transitional window should be
short and the eFuse burn prompt.
